- Every new function is born without visitor access (default privileges revoke EXECUTE from PUBLIC and anon for functions created by postgres); open one to visitors only with a written justification and by adding it to FUNCOES_PUBLICAS in src/lib/funcoesPublicasSql.test.ts. Functions outside schema public get no PUBLIC EXECUTE either, so GRANT authenticated/service_role explicitly. Why: the Data API exposes every granted function to visitors.
- Anon-callable SECURITY DEFINER functions must check auth.uid() and company inside (no "auth.uid() IS NULL" bypass); helpers called only by other definer RPCs or triggers get no anon/PUBLIC (or authenticated, for seeds) EXECUTE. Why: visitors and other companies must not reach company data.
- Portal passwords live only as bcrypt in external_accesses.access_password_hash (access_password is a retired, column-revoked backup that new writes leave empty); verify only through portal__verificar (server-side failure log, 10/5 min lock, uniform invalid_password); create/regenerate only via portal_acesso_* RPCs, which return the plaintext once; screens select EXTERNAL_ACCESS_COLUMNS. Why: no screen, log or role can read a stored portal password.
- Authenticated-callable SECURITY DEFINER functions that receive a company or record id must match it to get_user_company_id(auth.uid()) (only service_role and no-JWT internal contexts bypass), returning empty/false or 42501; helpers used only inside other definer functions get no authenticated EXECUTE. Why: public company signup means any logged user may belong to another company.
- Partner tables: browser access is column-granted and gated by perm_modulo('portals', …) (managers included); partner_orders received data is immutable and status moves only received→processing/processed/error, processing→processed/error/received, error→received (partner_orders_guarda, which stamps processado_*/situacao_alterada_*); integration_oauth_clients.secret_hash is never granted to browser roles; api_partners credentials and archive columns change only through server RPCs, and a new partner's credential is normalized by api_partners_insercao_guarda (only a fresh unlinked client created by the same user). Why: ordinary members could rewrite orders, read secret hashes and edit partners.
