- Conservação do tubo do apoio é calculada por trigger em apoio_recipiente a partir da etiqueta EPL (tabela editável em apoio_laboratorio.conservacao_textos) — assim a transmissão e o XML ao Pardini não mudam.
- Triagem Lab: unidade = origem (`origins.papel_*`, `laboratorio_destino_id`); permissões em `permissions.triagem`, checadas no banco por `triagem_tem_permissao`; auditoria reaproveita `apoio_auditar` → `apoio_auditoria`. Why: não duplicar cadastro de unidades nem trilha de auditoria.
- Horário de coleta: único campo `collectedAt` (+ `collectedBy`) no exame em `lab_guides`; correção só via RPC `lab_coleta_corrigir_horario` (justificativa + auditoria). Why: é o campo que o Apoio envia como DataColeta/HoraColeta.
- Nutrição: pacientes vêm dos leitos ocupados (inpatient_beds.current_request_id → admission_requests); dieta em nutricao_paciente, conferido/servido só via RPC nutricao_marcar (permissões em permissions.nutrition, checadas por nutricao_tem_permissao). Why: lista igual à Internação, sem cadastro duplicado.
- Internação/Regulação: ações aprovar/recusar/confirmar chegada/alta checadas no banco por `internacao_tem_permissao('approve')`, fechado por padrão (admin total). Why: sem acesso por fora da tela.
- Fila do Médico: vem de `triage_entries` status in_doctor (setor em destination_sector_id), ordem cor → espera. Why: fila real da Triagem.
- WhatsApp: liberação/cota/solicitações só via RPCs whatsapp_* (Super Admin checado no banco); tokens e fila base sem acesso do navegador, que lê só whatsapp_fila_envios_v mascarada. Why: LGPD e nenhuma credencial uazapi exposta.
- WhatsApp fila de confirmação: só via RPCs whatsapp_enfileirar_confirmacao / whatsapp_cancelar_envios_agendamento / whatsapp_reenfileirar_confirmacao, chamadas a partir do SchedulingContext (salvar, mudar status, remarcar). Why: company_id e telefone ficam no servidor; um único ponto cobre todas as telas.
- InovaChat: gravação só via inovachat_registrar (service role), chamada pelo whatsapp-webhook e por trigger em whatsapp_fila_envios para mensagens do sistema; navegador recebe ao vivo só inovachat_sinais (sem texto/telefone). Why: um ponto idempotente e LGPD no canal ao vivo.
- InovaChat atendimento: envio só pela Edge Function inovachat-enviar (valida/assume via inovachat_preparar_envio com o login do usuário; grava via inovachat_gravar_envio só service role); assumir/transferir/finalizar/reabrir só por RPCs inovachat_*; eventos internos são linhas origem 'evento' em whatsapp_mensagens. Why: toda regra no servidor e assumir atômico.
- InovaChat colors: view-local CSS tokens, never stored. Why: isolate presentation.
- InovaChat mídia: bucket privado inovachat-midia sem policies; navegador só recebe URL assinada curta via Edge Function inovachat-midia (escopo checado em inovachat_midia_acesso / inovachat_pode_enviar); baixa por inovachat-midia-worker acordado pelo webhook (backstop de hora em hora). Why: LGPD e nenhum acesso direto ao arquivo.
- InovaChat horário/retenção/exclusão: fora do horário decidido só em inovachat_fora_horario_avaliar (horário da empresa com override opcional por setor); retenção pela Edge Function inovachat-retencao com modo global em whatsapp_config_global.retencao_modo (padrão simulação); exclusão do titular só via inovachat-excluir-contato. Why: regras e exclusões sempre no servidor.
- Cycle automation: categories derived centrally by whatsapp_automacao_categoria (frequency counts only relationship rows); stop buttons use shared whatsappCiclo helpers and the exact trailing SQL opt-out footer. Why: new types inherit rules without duplication; queued preferences preserved.
- Subdirectories have their own AGENTS.md (e.g. supabase/functions/); read it before changing files there.
- WhatsApp/InovaChat/CRM functions: every new one is born with REVOKE EXECUTE FROM PUBLIC, anon in the same migration (trigger functions also FROM authenticated); company/user params must be guarded by auth.jwt() IS NULL OR service_role OR same company/user as auth.uid(). Why: block functions were callable without login, leaking names and cross-company data.
- SQL tests: PGlite via `bunx vitest run --config vitest.sql.config.ts`, separate from browser tests. Why: no operational writes or messages.
- NPS uses whatsapp_nps_processar before confirmation; tests use whatsapp_nps_teste_processar with validated queue snapshots and source locks, without scores/alerts. Links use whatsapp_render_links/renderLinks. Cleanup anonymizes before queue deletion (fila_id has no cascade); whatsapp_nps_conversa enforces sector visibility. Why: prevent duplicates, protect contacts and statistics.
- CRM: RPC writes and company permissions; isolated message/appointment hooks; stable stage events; aggregate results; deduped daily alerts; live crm_sinais. Why: privacy, no blocked clinical actions.
- WhatsApp removal: shared remote flow; service-only local RPC atomically deletes the instance/token and writes masked audit after remote success. CRM defaults retain a company creation marker. InovaChat titles use linked patient joins; notification inserts enrich only linked conversations. Why: failure safety, legacy configuration preservation and scoped presentation.
- Result entry uses labExamWorkbench: frozen destination first, catalog fallback for incomplete items; shared page/modal filter. Why: Edit Guide exams stay visible without collection changes.
